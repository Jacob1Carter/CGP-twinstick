The system we are using in Unity today captures inputs in floats, meaning that - if we take the arrow keys as reference - the float value associated with the left and right arrow will be some value between -1 and 1; where -1 is moving left fully (left arrow pressed), 1 is moving right fully (right arrow pressed), and 0 is stationary (no horizontal input pressed). The values that are not -1, 0, or 1 are often achieved through controller sticks, with their more precise inputs.

For a game, these problems are by no means ideal. Let's address them in turn.
Why is it moving so quickly?

The Update() function runs once per frame. If your game is running at 300 frames per second - which really isn't unheard of - then we're trying to translate the player EVERY FRAME (via Update()). That's.... a lot, hence the insanely quick movement.

Multiplying a value by Time.deltaTime in this manner makes it run once per second instead of once per frame. This will appear on the Unity Certification. So, anywhere you want to do something over time in Update(), you use this technique. This technique is known as frame-rate independent. Your player will still move quickly due to a second bug, which we will get to momentarily - the above is essential, however.
The reason we can move through the wall is because our player does not care for physics at this point. The player has no idea what a collision is, nor where the walls are - it simply is told - in code - to move in a direction, and so it does, regardless of wall or obstacle placement.
